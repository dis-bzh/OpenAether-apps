# Key inventory, crypto-periods and compromise procedures (apps side)

Every cryptographic secret that the **applications repository** creates or depends on: what it is, where it lives, how long
it is meant to live, what its loss or leak costs, and how to replace it. The keys of the platform underneath (Talos PKI and
secrets bundle, etcd secretbox key, system-disk and tfstate passphrases, SSH and bastion keys) are inventoried in
`OpenAether-infra/docs/key-management.md`; this file does not copy them.

Reading the table: **Period** is the intended lifetime. Where the code enforces nothing, the value is a *proposal* (marked
"proposed"), the owner's to confirm; ANSSI's rules ask for a stated period, not for this one. **Not run** means the
procedure is written from the tools' documentation and the code, and was not executed on a cluster.

## Inventory

| Key | Purpose | Generated by / where it lives | Algorithm | Period | If lost | If leaked | Archive / erasure |
|---|---|---|---|---|---|---|---|
| **OpenBao seal key** | Unwraps OpenBao's barrier key at every start | `init.sh`, 32 random bytes; Secret `openbao-seal-key` (foundation-vault); escrow off-cluster, two custodians at least, proven by a hash and attested in the ConfigMap `openbao-escrow-ack`, checked daily (README, Day 0) | AES-256-GCM wrap (upstream implementation of the static seal) | none enforced; rotate on any exposure; proposed: yearly | Every secret in OpenBao and every raft snapshot is unreadable | Whoever also gets a snapshot or the raft PVC opens all of OpenBao | Escrow copies are the archive; old keys are `previous-key` for one roll only, then dropped |
| **Recovery shares** | Quorum for the break-glass root token and recovery operations | `sys/init`; Secret `openbao-recovery-shares`, each share PGP-encrypted to one operator | Shamir, N >= 3, threshold >= 2 | none; re-key when an operator leaves | Below quorum: no break-glass | A share alone is useless (PGP-encrypted); T holders' private keys together are root | Keep the encrypted copy off-cluster |
| **Offline root CA** | Signs the OpenBao intermediate | Operator, [runbook](../apps/base/foundation/vault/pki-root-offline-runbook.md); token, offline media or (deviation) password manager | ECDSA P-384 or RSA 4096, SHA-384 | 10 years | Cannot renew the intermediate: new root, new trust anchor | Attacker can mint trusted certificates | Destroy media/token at end of life |
| **OpenBao intermediate CA** | Signs leaf certificates (`pki/sign/openaether`) | OpenBao (`pki/`), key in the raft data (protected by the seal key) | ECDSA P-384 for a new intermediate (`OA_PKI_KEY_TYPE=ec`; a cluster created before keeps its RSA-2048 one until it is regenerated: runbook section 5) | 730 days (`ttl` 17520h) | Re-sign a new CSR with the root | Revoke through `pki/revoke` (CRL, OCSP and AIA URLs are published) or replace it: runbook section 6 | Raft snapshots keep old keys for as long as they are retained |

| **OpenBao listener / bundle certs** (`openbao-server-tls`, `openbao-ca-bundle`) | TLS of the OpenBao listener; CA bundle for the Gateway | cert-manager from `openbao-ca` | ECDSA P-256 | 8760 h, renewed 720 h before | Re-issued automatically | Re-issue | Not archived |

A CA plugged from OpenBao is not done: recorded deviation |
| **Raft snapshots** (`openbao-snapshot`) | Backup of OpenBao | CronJob, restic repositories | barrier encryption (seal key) then restic | restic policy: 14 d, 8 weeks, 12 months | See backup README | Readable only with the seal key AND the restic password | Retention above; bucket emptying on decommission (backup README) |

| **Loki / CNPG S3 credentials** (`loki-s3-credentials`, `cnpg-backup-s3`) | Log chunks; WAL archive and base backups | Operator; OpenBao (seeded by the infra tooling) | provider API keys | as above | Logs / PITR stop | Read logs; read or delete the WAL archive (barman objects are not client-side encrypted, backup README) | Revoke at the provider |
| **Zitadel masterkey** | Encrypts secrets stored in Zitadel's database | `configure.sh`, 32 characters at `secret/zitadel/masterkey`; ESO Secret `zitadel-masterkey` | Zitadel's own use (32 bytes) | none; **no rotation known** | The database restore is unusable without it, so the OpenBao snapshot comes back FIRST | Combined with a database dump, opens Zitadel's encrypted fields | Same as OpenBao snapshots |
| **Database passwords** (`secret/zitadel/db`, `secret/grafana/db`) | CNPG application roles | `configure.sh`; ESO | 32 alphanumeric characters | none; rotate on exposure | A restore of the databases needs the same roles | Database access | Not archived |
| **Zitadel first admin** (`secret/zitadel/admin`) | INITIAL password of the first human admin | `configure.sh`; ESO. | **Grafana admin, MinIO root** (`secret/grafana/admin`, `secret/minio/root`) | Local admin logins | `configure.sh`; ESO | 32 characters | none; rotate on exposure | Read it back with `openaether-admin` | Admin of Grafana / MinIO | Not archived |
| **Grafana OIDC client secret** (`secret/grafana/oidc`) | Grafana against Zitadel | Operator, from the Zitadel console | Zitadel-generated | proposed: yearly | SSO stops, the local login stays | Impersonate Grafana to Zitadel | Regenerate in Zitadel |
| **Longhorn LUKS passphrase** (`secret/longhorn/encryption`) | One passphrase for ALL encrypted volumes | `configure.sh`, 48 characters; ESO Secret `longhorn-encryption` | aes-xts-plain64, 512-bit key, sha256, argon2id (set in the Secret, applied at first format) | none; **do not change it while encrypted volumes exist** (below) | Every encrypted volume is unreadable | All volumes open to whoever has the volume data too | Escrow with the other Day-0 items is advisable; not in the Day-0 list today |
| **Grafana `secret_key`** | Encrypts values Grafana stores in its database | Not set in this repository: upstream's published default applies | upstream default | n/a | n/a | The default is public: set one before storing a secret in Grafana's database | Gap, not changed here (what Grafana stores encrypted in this deployment is to be checked) |

Cryptographic posture, stated: everything above is classical (no post-quantum hybrid key establishment on the gateway, OpenBao
listener or mesh), and certificate signatures are SHA-256 except those the offline-root runbook now makes SHA-384. ANSSI asks
for hybrid key establishment where recorded traffic would still matter in the long term. Not done; to be revisited with the
Envoy, ztunnel and OpenBao releases that support it (ANSSI TLS-19).

## Recorded deviations

| Deviation | Why | Revisit |
|---|---|---|
| The seal key is a software key in the cluster, not an HSM or an external KMS; the barrier is wrapped with AES-GCM rather than a key-wrap mode | Self-contained, hands-free restarts; the wrap is the upstream seal implementation | A `transit` seal against an OpenBao or KMS outside the cluster (README, "Limits"; migration untested here). If upstream offers a key-wrap mode |
| Root CA custody may be a password manager | Small deployments; the runbook recommends a token or offline media | When a second operator and a token exist |
| `openbao-ca` (listener) is separate from the OpenBao PKI | OpenBao needs a certificate to start, and its own PKI is inside it | Never, unless OpenBao is started with a different listener bootstrap |
| The Istio CA is istiod's self-generated one | Default, no extra moving part | When the mesh must trust the OpenBao PKI |
| Machine secrets reach new nodes through the Talos maintenance API, unauthenticated at that moment (infra) | Upstream design; compensated by the private network, the SSH tunnel and the bastion ACL | Documented in the infra repository |

## Replacing a key

An operator holding `openaether-admin` rotates, checks, and records the date in the incident register if it was an incident
(`OpenAether-infra/docs/incident-response.md`). Target after a compromise: about a day (ANSSI PG-078 R26). All rotations below
are **Not run**.

Writing a new value into a created-only secret: `configure.sh` never overwrites (`cas=0`), so use the admin identity
(`bao_admin` in the vault README) to write a **new version** of the path, then let External Secrets refresh (`refreshInterval`
1 h, or `kubectl annotate externalsecret <name> force-sync=$(date +%s) --overwrite`) and restart the consumer.

- **Seal key**: vault README, "Seal key rotation" (run twice on a cluster). Then redo the Day-0 escrow and re-attest it.
- **Recovery shares / a departed operator**: with a break-glass quorum that does not need the departed operator, generate a root
  token, `bao operator rekey` the recovery keys to the new PGP set, revoke the root token. Update `openbao-operator-keys` for
  future clusters. A recovery share cannot be revoked, only superseded.
- **restic password**: `restic key add` with a new password on each repository, check it opens, `restic key remove` the old
  one; write the new value as a new version of `secret/backup/restic`; refresh `backup-restic-env`. A leaked password on a
  repository an attacker could also read means the old snapshots stay readable by them: start a NEW repository (new path) and
  keep the old one only until the retention of the new one covers your need, then empty and delete the old bucket path.
- **Backup / Loki / CNPG S3 keys**: create a new key at the provider, write it as a new version of its path, refresh, confirm
  a backup run succeeds, revoke the old key at the provider. Order matters: revoke last.
- **Database passwords**: the role password lives in two places (OpenBao and PostgreSQL). Change it in PostgreSQL
  (`ALTER ROLE`), write the new version, refresh, restart the consumer; between the two steps the consumer fails.
- **Zitadel masterkey**: no supported rotation is known to this repository (not verified against Zitadel's documentation); the
  key encrypts what is already in the database, so replacing the OpenBao value breaks Zitadel. After a leak: treat as a rebuild
  of the identity layer from the database restore plan, or ask Zitadel's support channels first.
- **Longhorn passphrase**: Longhorn's volume-encryption documentation says nothing about changing the passphrase of an existing
  volume. This deployment hands ONE Secret to every volume's node-stage step, so a new value would be presented to volumes
  whose LUKS header still holds the old one (reasoned from the mechanism, not tested): they would fail to attach. Do not
  write a new version while encrypted volumes exist. A change means a new StorageClass with a new Secret and a data migration.
- **Offline root / intermediate / `openbao-ca`**: root CA runbook, sections 5 and 6. `openbao-ca` is renewed by cert-manager a
  year before it expires; for a compromise delete the `openbao-ca` Secret (cert-manager re-issues; restart OpenBao and its
  clients to pick up the bundle).
- **Grafana / MinIO admin passwords**: write a new version and refresh; Grafana reads `existingSecret` at start, restart it.
- **Revoking an operator's access to the cluster**: infra (`bastion_ssh_keys`, kubeconfig/talosconfig CA rotation).

## Review

Re-read this file with every change that adds a Secret, a Certificate or a seeded OpenBao path (`configure.sh`), at each seal-key
rotation, and at least yearly. A row without a period, an impact or a replacement procedure is a defect.
