# apps/flux — Flux DAG and modular brick picking

The only fixed baseline is **CNI (Cilium) + Flux**, injected at bootstrap by
`OpenAether-infra` (Talos inlineManifests). Everything else can be **picked**:
a cluster installs only the bricks it wants, and their dependencies follow
automatically.

## Layout

- `base/` — the full DAG (source of truth): numbered Flux Kustomizations,
  dependencies encoded in `spec.dependsOn`.
- `bricks.yaml` — the picker's UX catalogue: aliases, baseline, companions,
  descriptions. **Never dependencies here** (they live in `dependsOn`).
- `management/` — overlay of the management cluster (the full DAG except the opt-in Forgejo git forge).
- `management-forge/` — `management` plus the opt-in Forgejo git forge (`forgejo-db`, `forgejo`), `docs/forgejo.md`.
- `workload/` — overlay(s) of the client clusters (reduced profiles).
- `local/` — local Docker/WSL2 overlay (everything suspended, manual apply).
- `<profile>/` — profiles generated by the picker (see below).

## Picking: `scripts/pick.py`

```bash
python3 scripts/pick.py --list                  # bricks, aliases, dependencies
python3 scripts/pick.py --validate              # DAG + catalogue health
python3 scripts/pick.py --check                 # generated profiles up to date? (CI)
python3 scripts/pick.py vault gateway           # plan (dry-run)
python3 scripts/pick.py zitadel -o apps/flux/edge   # generates the `edge` profile
```

`--validate` + `--check` are grouped in `task apps-validate` (Taskfile of
`OpenAether-infra`) — run them after any change to the DAG.

Automatic resolution: the **transitive closure** of `dependsOn` is included
(picking `zitadel` pulls in cnpg, istio, services-gateway, OpenBao, ESO, the
PKI…). On top of that come:

- the **security baseline** (`baseline`: namespaces, default-deny, flux-egress),
  which `--no-baseline` turns off (not recommended);
- the **companions** (`companions`): configuration bricks added as soon as all
  their dependencies are already selected (e.g. `external-secrets-stores` when
  ESO **and** OpenBao are picked), never drivers of new dependencies.

The generated profile references the whole of `../base` and **removes**
(`$patch: delete`) the Kustomizations that were not picked: no duplication, the
base stays the single source of truth, and no retained Kustomization depends on
a removed one. Compatible with `kubectl kustomize` (no file reference outside
the root).

**Opt-in bricks.** The Forgejo git forge (`forgejo-db`, `forgejo`; alias `forge`) is in the DAG and in the catalogue but OFF in the
`management` and `workload` profiles (0.4.0 release gate: it adds +400 m of CPU requests and has never run on a cluster). To run it,
point the root Kustomization at `apps/flux/management-forge`, or generate a profile that picks it
(`python3 scripts/pick.py forge <other bricks> -o apps/flux/<name>`), or reference `management-forge` from the instance repository's
own profile. `docs/forgejo.md` has the consequences (capacity, the volume's recurring backup, what the lab must prove).

To enable a profile: point the root Flux Kustomization at its path
(`spec.path: ./apps/flux/<profile>`) on the `OpenAether-infra` side
(bootstrap-manifests), or through an overlay patch.

## Health gates

A Kustomization without `wait: true` or `healthChecks` is "Ready" as soon as its objects are applied, not when they work. In
the `apps/flux/management` render (40 Kustomizations) these 14 have no health gate:

On a real management cluster `OpenAether-infra` adds a 15th (`openaether-platform`), absent from this repository: 15 of 40.
Adding or removing a `wait`/`healthChecks` changes this list; the test fails until it is updated.

A gate is only as good as the verdict on each object. Two traps, both read in the sources of Flux 2.9.6 and 2.10.0:
with `wait: true` the controller **ignores** `spec.healthChecks` (an entry next to it gates nothing), and a custom resource
with no Ready condition yet counts as "Current", so an operator that has not touched its CR would pass the gate. Read in the
sources, not yet shown on a cluster.

**The `cnpg` gate. This is the one text on it**: `apps/flux/base/20-cnpg.yaml` and `scripts/dev/test-flux-health-gates.sh`
point here.

- **Why.** `wait: true` also checks `zitadel-db` and `grafana-db`, and a CNPG `Cluster` gets its Ready condition with its
  FIRST phase (read in CloudNativePG 1.30.1; not yet shown on a cluster). Lab 32 (N1) is consistent with it: `cnpg` was
  Ready after 47 s, both Clusters were 3 of 3 about 9 minutes later, and the dependents started on databases that did not
  exist (Grafana restarted 6 times); the cause there is inferred, not observed. In labs 29-31 it became Ready 2-6 s after
  both were 3 of 3.
- **The entry.** `cnpg` carries a `healthCheckExprs` entry for the `Cluster` kind (kustomize-controller v1.9.6 and v1.10.1,
  same code). Current only when the Ready condition is `True`, which CNPG sets with the phase "Cluster in healthy state";
  anything else, an empty status included, is InProgress. With no `status` key at all the expression errors, Flux reads
  Unknown and keeps waiting, as wanted. Write it with `exists`, never `filter(...).all(...)`: `all` is true on a list with
  no Ready condition, the very hole. A healthy Cluster is Ready=True and passes at the first poll; one in a rolling update
  was already InProgress for kstatus (Ready=False), so nothing becomes NotReady that was not before.
- **The timeout.** `15m` now has to cover the databases: 5:52-6:16 (Scaleway, labs 29-31), 7:19 (OVH, lab 28), 10:02 in
  lab 32 with the released dependents on the same nodes (not shown to be the cause). Past it the Kustomization fails, is
  retried every 2m and passes as soon as both are Ready; nothing is rolled back, its dependents only wait. Their wait is
  silent: the Flux alerts (FluxObjectNotReady, FluxReconciliationStalled) are rules of the observability bricks, which
  depend on this Kustomization, so read `kubectl -n flux-system get kustomization cnpg` directly when the databases are slow.
- **The pin.** `scripts/dev/test-flux-health-gates.sh` pins that entry string for string and checks `timeout` >= 15m.

## Invariant to maintain

**`dependsOn` = real dependencies**, not merely a convergence order. Every new
brick must declare *everything* it requires: StorageClass
(`platform-local-path-provisioner`), PriorityClass (`platform-priority-classes`
— a missing PriorityClass makes admission reject the pod), LB pool
(`platform-cilium-lb-ipam`), and so on. That is what makes picking safe.
`scripts/pick.py --validate` checks integrity (cycles, unknown targets, dead
paths, files not wired into `base/kustomization.yaml`).

**A generated profile freezes the list of EXCLUDED Kustomizations**: adding a
brick to the DAG therefore makes every profile already generated stale — the new
brick is inherited from `../base` without having been picked, and stays stuck if
its own dependencies are excluded. This happened for real with `orc` (which
depends on `cluster-api-providers`, absent from the workload clusters): it
blocked both edge clusters. `scripts/pick.py --check` replays the generation in
memory from each profile's `# Pick:` header and exits 1 if one has diverged —
**regenerating the profiles is part of every DAG change**.
